# Tastrade — documentation project config

Read by the `document-vfp-artifact` skill (`.claude/skills/document-vfp-artifact/`)
before any doc is written. Everything specific to this app lives here; the
skill itself is app-agnostic and comes from the
[vfp-documentation-toolkit](https://github.com/jefflroberts/vfp-documentation-toolkit).

## App

- **Name:** Tastrade (Tasmanian Traders)
- **Origin:** Microsoft sample application shipped with Visual FoxPro 5, 6,
  and 7. Copyright Microsoft Corporation 1995. VFP 9 ships only its data.
- **VFP version:** Binaries last written 1997 to 1998 (VFP 6 era), shipped
  with VFP 7 in 2001. Rebuilt under VFP 9 SP2 on 2026-09-08 with no source
  changes; see `JOURNAL.md` Step 3.
- **What it does:** Order entry and customer management for a fictional
  importer. Maintains customers, employees, products, suppliers, shippers,
  and categories; takes orders with line items; prints invoices, lists, and
  sales reports. Includes a login with user levels, an intro screen, a
  "behind the scenes" self-documentation form, and a case study viewer.
  It exists to demonstrate VFP's object-oriented framework style: an
  application object, an environment object, a base form class hierarchy,
  and a navigation toolbar.

## Data access convention

Forms open tables through their DataEnvironment, and the base form class
`tsbaseform` (in `libs/tsbase.vc2`) manages the record pointer, buffering,
and the navigation toolbar. Stored procedures in the DBC (`NewID`,
`ValOrder`, `CalcOrdTotal`, `RemainingCredit`, ...) implement the business
rules and are wired to triggers and validation rules. Flag any form or
method that does its own `USE`, `SELECT N`, or hand-rolled ID generation
instead.

## App-specific gotchas

- **Two forms bypass the framework.** `forms/getinv.sc2` (class `form1`) and
  `forms/gettitle.sc2` (`frmgettitle`) inherit from the VFP `form` base
  class directly, not from `tsbaseform`. They are the report parameter
  dialogs that the data environment `Init` of `reports/orders.frx` and
  `reports/listempl.frx` run. Say so; do not describe them as framework forms.
- **Framework lives in two libraries.** `libs/tsbase.vc2` has the visual base
  classes (17 classes: `tsbaseform`, `tsmaintform`, `tstextform`,
  `tsformretval`, `tstoolbar`, and one subclass per VFP control).
  `libs/tsgen.vc2` has the non-visual and composite classes (8: `application`,
  `environment`, `customerinfo`, `daterange`, `findcustomer`, `findorder`,
  `introform`, `splitter`). `libs/main.vc2` holds only `tastrade AS
  application`, the concrete app object that `progs/main.prg` instantiates.
- **Form names differ from file names.** `customer.scx` is `frmcustomers`,
  `rebuild.scx` is `frmdatabaseutils`, `behindsc.scx` is `frmbehindsc`.
  Use the file name for the doc file and the class name in the header.
- **`ORDER_LINE_ITEMS` is `orditems.dbf` and `USER_LEVEL` is `user_lev.dbf`.**
  The DBC's long table names differ from the 8.3 file names. Doc files use
  the DBC table name lowercased.
- **Include files carry the strings.** `include/strings.h` defines every
  user-visible string as a `_LOC` constant; `include/tastrade.h` defines the
  rest and sets `DEBUGMODE .T.`. Resolve constants when quoting code.
- **The app reads INI and registry.** `progs/main.prg` declares Win32 API
  calls for private INI files and the registry, and reads `tastrade.ini`.
- **Menus:** `menus/navigate.mn2` and `menus/window.mn2` have no generated
  `.mpr` in the repo (the build generates them; the EXE has their strings).
  Three pads reuse system pad names as a placement trick: Administration is
  `_msm_file`, Navigation `_msm_edit`, Help `_msm_systm`. The main menu's
  cleanup code is the only privilege gating, and its `RELEASE BAR ... OF
  ADMINBAR_LOC` lines name a popup that does not exist. See `docs/07-menus/`.
- **Self-documentation.** `behindsc.dbf` and the `frmbehindsc` form are the
  sample's own "behind the scenes" explanations of its design; `casestdy`
  and `viewcode` display text from tables and reports. They are part of the
  sample's teaching purpose, not business function.

## App-specific landmines

- Saved printer environments in the reports. All thirteen embed one: seven
  name `\\MSPRINT32\2/1MC PRIVJ 157.56.32.242`, three `LaserNT`,
  `viewcode.frx` an HP LaserJet 4Si on `\\msprint32\privj`, and
  `orders.frx` `\\RED-PRN-16\CORP0007`, a Microsoft print server from 2001.
  The record is stored twice (text `expr` and binary DEVNAMES `tag`);
  `casestdy.frx`'s two halves disagree. Documented in `docs/06-reports/`.
- Report data environments declare cursors (12 of 13) and two run parameter
  dialogs from `Init`; `listempl.frx`'s `Init` uses include-file constants
  without an `#INCLUDE`, so its "nothing to print" path errors.
- `HOME() + "Samples\Tastrade\"` paths in report data environment code,
  which assume the sample sits under the VFP install folder.
- The `fontface` attribute of `reports/orders.fr2`'s data environment record
  now holds the VFP 9 compiler's include-file table with an absolute path.
  Build noise; ignore.
- `WEXIST("Project Manager")` checks in report code that change behaviour
  depending on whether the IDE is open.
